# 交流实录稿分支合同

## 目标

把商务、客户、销售、合作、访谈或普通多人对话整理成可回看、可追溯、仍有交流推进感的实录。它不是会议摘要，也不是原文搬运。

## 写稿前

1. 建立人物关系、第一人称锚点和低置信策略。
2. 人数多于 ASR 声道或标签无法稳定对应真人时，按公共流程建立并校验 `speaker-map.json`。人物未锁定时只用“说话人A”等标签，禁止猜姓名。
3. 按自然话题建立 `Sxx` 源段，记录起止时间、主要说话人和必留事实。
4. 列出关键问答、数字价格、案例、异议、承诺边界和下一步。

## 输出合同

```markdown
# 标题｜交流实录稿

## 话题名称 [00:00:00-00:10:00]

**说话人：** 连续发言合并为一个发言块，保留问题、回应、追问和转折。

## 人物关系与低置信说明
...

## 疑似识别错误与修正说明
...
```

硬要求：

- 每个正文二级标题带合法、递增的起止时间；范围可用 `-`、`~`、`～` 或 `—`。
- 时间戳只放大主题标题；独立时间戳和说话人行内时间戳均不合格。
- 连续同一说话人、同一话题且无中间互动的碎句必须合并。
- 保留问答推进、分歧变化、异议处理和决策形成过程。
- 销售观察、风险、待办和其他附录放正文后，不作为新的时间话题。
- 人物映射被用户纠正后，旧稿必须全局重检，不得只改一处姓名。

## 删留标准

详细保留有信息量的提问、回答、追问、反驳、案例、数字、价格、承诺和下一步；压缩无业务信息的口头重复、碎句和寒暄；删除与人物关系、决策链和推进条件无关的插曲。

## 质量闸门

从开头、中段、结尾各抽一个高信息片段回到原文，检查人物、问答、数字、案例和承诺。保留率低于 35% 或高于 80% 只触发复核，不能单独判定失败或成功。

普通交流：

```powershell
python scripts/validate_transcript_artifact.py --mode exchange --draft refined.md --source original.txt --json
```

复杂多人交流必须追加 `--speaker-map`、`--people-count` 和 `--asr-channel-count`。

## 失败模式与自修

- 只剩观点和表格：回到每个 `Sxx` 补回关键问答。
- 大量口水词和碎句：重新执行机械清理和连续发言合并。
- 未锁定却出现姓名：恢复低置信标签，重建人物表后全局复查。
- 为满足比例重复堆字：删除重复，按证据覆盖修复。

销售型交流需要判断客户顾虑和推进信号时，可追加读取 `../sales-review-transcripts.md`；主稿仍执行本合同。
